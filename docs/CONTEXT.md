# 超长上下文

移植自 VPetLLM，加了一层终端场景特有的东西。

---

## 0. 手机场景的两个额外约束

VPetLLM 跑在桌面上，连的多半是云端 API。手机上不一样：

1. **窗口可能极小。** 用户很可能连的是本机 llama.cpp / MLC / Ollama，
   `n_ctx` 常常只有 2048~4096。任何"默认按 128k 规划"的设计都会当场崩。
2. **终端输出是上下文杀手。** 一次 `pip install torch` 吐 ~15k token，
   一次 `find /` 吐 ~100k。这是聊天场景根本不存在的问题。

第 1 条决定了 `ContextLimitGuard` 从「锦上添花」变成「必需」；
第 2 条催生了 `OutputDistiller` 这个 VPetLLM 里没有的部件。

---

## 1. ContextLimitGuard —— 读窗口，也校准尺子

服务端在拒绝我们时其实把答案写在脸上：

```json
{"error":{"message":"request (13392 tokens) exceeds the available context size
 (8192 tokens)","type":"exceed_context_size_error",
 "n_prompt_tokens":13392,"n_ctx":8192}}
```

而且撞上之后**每一轮都会再撞一次** —— 历史只增不减，
错误信息里明明写着 8192，却没有任何一处代码去读它。

### 两段式

**第一段：读 `n_ctx`。** 正则从结构化字段优先，散文次之。抠不到就返回 0 而不是猜 ——
有些网关只说「太长了」不给数字，那种情况没有可信的裁剪目标，盲目对折会把一个
200k 窗口的模型砍成 100k，白白浪费。

**第二段（关键）：用 `n_prompt_tokens` 校准我们的估算器。**

光知道窗口是 8192 不够用。`TokenCounter` 是估算的，对中文、代码、base64 的偏差都不一样。
按自己的尺子量出 5000 以为没超，照发不误，然后再挨一次 400。

```
ratio  = serverTokens / ourEstimate    // 13392 / 9500 = 1.41
budget = n_ctx / ratio                 // 8192 / 1.41 = 5810
```

`ratio` **取历史最大值而不是最新值**：估算器只会偏低不会偏高（对未知 token 保守），
所以观测到 1.41 之后又观测到 1.10，更可能是那次 prompt 恰好好分词，而不是估算器变准了。

### 撞第二次怎么办

同一个上限重复撞，说明 ratio 还不够准（一个全局倍率注定有残差）。
按 hits 递减收紧：`0.90 → 0.75 → 0.60 → 0.50`，下限 512 token
（再小连当前这轮提问都放不下，变成「裁到空还是发不出去」的死循环）。

### 按「渠道|主机|模型」分桶

不能只按 provider 记：同一个 provider 下不同节点的窗口能差一个数量级
（一个 8k 的本地节点和一个 200k 的云端节点），混着记会把大窗口的节点也裁短。

学到的值**只活在本进程内**。服务端换配置、用户换节点都会让它失效，持久化弊大于利。

## 2. OverflowManager —— 滚动摘要 + 滑动窗口

阈值 T：prompt 窗口只装 checkpoint 之后的消息；累计到 2T 时触发一次增量摘要，
checkpoint 前移到「保留最近 T」的位置。

### 为什么是滚动摘要而不是摘要链

摘要链（把每段摘要拼起来）会无限增长，最终摘要本身撑爆窗口，而且早期措辞被反复重复。
滚动版每次把当前摘要连同新溢出的消息一起喂回去，产出一份**完整的新版本**取代旧版本 ——
每次都有机会重新组织全局信息，让重要的沉淀、过时的自然脱落。

### 为什么保留最近 T 而不是全摘完

全摘完会让模型丢失刚刚几轮的原文，而那几轮往往正是当前任务的上下文。

### 摘要要标注「这是过去的」

```
[更早对话的摘要 —— 这些是已经过去的内容，不是刚刚发生的]
...
[摘要结束。如需其中未涵盖的细节，调用 recall_memory 检索原始记录]
```

不标注的话模型会把摘要内容当成刚说过的话，时间感全乱 ——
表现为它会说「你刚才提到…」而那其实是半小时前的事。

### 为终端 Agent 改写的摘要提示词

通用的「总结以下对话」会产出对话流水账。Agent 需要的是**状态**：

- 用户目标和约束（永不压缩）
- 环境状态：cwd、已装的包及版本、已改的文件路径
- 已验证有效的命令
- **失败过的尝试及其原因** ← 这条最容易被摘要丢掉，丢了就会重蹈覆辙
- 未完成的待办

### 历史永不删除

被挤出窗口的消息完整留在数据库里，由 `MemoryRetrieval` 按需捞回。
**这是滚动摘要唯一的安全网** —— 摘要一定会丢细节，丢掉的细节必须能找回来。

### epoch 防复活

用户清空历史时 `_epoch++`。在途的摘要任务发现 epoch 变了就丢弃自己的结果，
否则一次慢的摘要请求会在清空之后把旧状态复活回来。

### 摘要失败绝不推进 checkpoint

推进了就是：那批消息被踢出窗口，而 `hasSummary` 为假，**没有任何摘要顶上**。
更糟的是 `AgentLoop._retrieveInto` 也以 `hasSummary` 为前提，安全网跟着一起失效 ——
被丢掉的内容连捞都捞不回来。宁可不压缩：窗口更满一点，至少内容还在。

「请求成功但正文是空的」按失败处理，两者的后果一模一样（摘要模型名填错时就是这样：
服务端 200，正文是空的）。

失败之后要**退避**一个阈值才重试。摘要失败通常是配置问题（地址、模型名、协议对不上），
不退避的话之后每加一条消息都白打一次请求，又慢又花钱，而且每次都失败。

原因存在 `lastError` 里给设置页看，另有 `takeUnreportedError()` 给状态条 —— 后者取一次
就没了，同一句话在状态条上刷十遍只会把别的状态挤掉。

### 摘要请求走 complete()，不自己拼请求体

曾经这里是手写的 OpenAI 请求，只特判了 ChatGPT OAuth，于是 Anthropic / Gemini 原生 /
Vertex 三种渠道的摘要请求全打到一个不存在的 `/chat/completions` 上 —— 404，
被 catch 掉返回空串，表现是「滚动摘要一次都不生效」，界面上没有任何迹象。

协议分派只该有一份。第二份迟早跟不上，而它已经漏了三种。

### 发请求之前也压一次，不只是回合结束后

只在回合结束后压的话，「该被压缩的那一次请求」恰恰是没被压缩的那一次。任何一个刚从库里
读回来的长会话都会撞上：摘要状态是 v12 才开始存的，在那之前的会话读回来一律是"还没摘过"，
于是第一次发送把整段历史原样发出去 —— 最贵、也最容易直接撞上窗口上限的一刻。

压缩排在检索**前面**：检索是把被摘要挤出去的东西捞回来，而这一刻可能刚好有一批被挤出去。

回合结束后那一次仍然留着 —— 一轮工具循环能往历史里塞几十条消息，不在结束时压一次的话，
它们要一直等到下一次发送。

### 摘要状态跟着会话落盘

`threads.summary` + `threads.summary_checkpoint`（库 v12）。只活在内存里的话，重开 app
或者切走再切回会话就归零 —— 长会话每次打开都要重新全量摘要一遍，而在那次摘要发生**之前**，
整段历史会原样发出去，恰恰是最容易撞窗口上限的那一刻。

checkpoint 是历史下标，恢复时要按当前历史长度夹一次；编辑重发、回到某条消息、切换分支
之后也要 `clampTo()`。越界的话 `history.skip()` 安静地返回空窗口 —— 模型当场失忆。

## 3. MemoryRetrieval —— 三路 RRF

```
final = 0.5·rrf + 0.25·importance + 0.25·recency
```

**三维求和而不是相乘**：任一维度低分不该把整体清零。一条很久以前记下、
但和当前问题高度相关的记忆仍应被召回；相乘的话 recency 一衰减就废了。

### rrf 融合三路

| 路 | 擅长 |
|---|---|
| BM25（IDF 加权） | 罕见词的单点强命中。"torch" 只出现在一条记忆里，"安装" 到处都是 |
| 覆盖率 | 把问题里的多个概念都提到了的文档 |
| 向量余弦（可选） | 零词法重叠的语义近邻 |

三者量纲互不相同（BM25 无上界、覆盖率 [0,1]、余弦 [-1,1]），直接加权求和没有意义。
**RRF 只看排名，天然免疫量纲问题。**

向量后端在手机上经常没有（本地 embedding 模型要额外几十 MB），
不可用时自动退成两路 —— 检索降级永远好过检索失败。

### 中文分词：单字 + bigram，不引词典

手机上引 jieba 词典要几 MB。BM25 的 IDF 机制对「单字 + bigram」的组合已经够用：
单字「装」到处都是 IDF 极低，bigram「安装」「装包」区分度就够了。

### 主动检索，不等模型自己调

`AgentLoop.send` 在有摘要时会先对用户输入跑一次检索并注入。
理由：**模型经常不知道自己忘了什么**，等它调 `recall_memory` 往往已经答错了。

## 4. OutputDistiller —— 本项目新增

### 问题的量级

| 命令 | 原始输出 |
|---|---|
| `pip install torch` | ~15k token（几乎全是 Collecting/Downloading/进度条） |
| `npm install` | ~30k token |
| `find / -name '*.so'` | ~100k token |
| 失败的 `make` | 几万 token，真正有用的是那 3 行 error |

8k 窗口的本地模型跑一条 `apt install` 就直接爆了。就算窗口够大，
把 15k token 的进度条塞进上下文也会让模型的注意力被噪声淹没。

### 顺序就是全部要点

```
1. \r 合并      —— 进度条是 \r 反复重写同一行，按 \n 切会得到几百个"同一行的瞬间"
2. 规则折叠      —— pip/apt/npm/编译/git 的逐条噪声
3. 重复行折叠    —— 规则没覆盖到的刷屏
4. 单行截断      —— base64 / minified JS / hex dump
5. head/tail 截断 + 中间的 error/warning 提取
```

**折叠必须跑在截断之前。** 清掉噪声之后往往就自然放得下了，根本不需要截断。
直接 head/tail 截断会把中间那 3 行 error 恰好切掉 —— 那正是唯一有用的部分。
所以第 5 步即使触发，也要单独把 middle 里的 error/warning 捞出来。

### 全文落盘 + grep_output

蒸馏后的输出带一个 `ref`，全文落在 objects 里。模型想看细节就调
`grep_output(ref, pattern)`，带前后 2 行上下文（一个 error 单独看往往没意义，
上一行的文件名和下一行的 note 才是关键）。

**没有 `grep_output`，蒸馏就是单纯的信息丢失。** 把细节挪出上下文的前提是
模型必须有办法主动拿回来。

### 摘要时用 ref 代替全文

`OverflowManager` 在构造摘要载荷时，工具输出只放首行 + ref。
它们已经被蒸馏过一次，再喂给摘要模型一遍纯属浪费；而且摘要模型很容易被
大段日志带偏，产出一份「关于日志内容」而不是「关于任务进展」的摘要。

### 沙箱拦截要点破

输出里出现 `Operation not permitted` / `Network is unreachable` 时，在头部加一行：

```
[沙箱拦截：可能是沙箱断网拦截。这不是网络故障，重试不会成功；
 需要网络请请求切换到联网档位]
```

seccomp 把 `socket()` 变成 `EPERM`，应用层看到的和真实网络故障长得一模一样。
不点破的话 LLM 会重试到天荒地老 —— 这是实际会烧掉大量 token 的一类失败。

## 5. 裁剪时的两条约束

`AgentLoop._trimTo`：

1. **system 消息永远保留** —— 它装着人格、工具约定和摘要，裁掉模型当场失忆。
2. **从尾部往前保留** —— 最近的消息是当前任务的上下文；从头保留会得到
   一堆和当下无关的开场白。

还有一条容易漏的：**工具 schema 也占上下文**。十个工具的 JSON schema
轻松上千 token。不算进预算会得出「还有余量」的错误结论
（`TokenCounter.estimateTools`）。

## 6. 撞超长只重试一次

裁完还超说明学到的 ratio 仍然不准，无限重试只会烧配额。
报错让用户看见、让 guard 记下 `hits+1`，下一轮的收紧系数会更狠。
